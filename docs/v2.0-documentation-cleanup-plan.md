# SJGV v2.0 documentation cleanup plan

**Status:** approved direction; execute after the v2.0 release snapshot  
**Scope:** documentation and demonstrably dead implementation paths only  
**Methodology effect:** none

## Objective

Make the final SJGV v2.0 methodology easy to read and hard to misinterpret. A
reader should be able to find every active construction rule in one concise
binding specification without working through the project's experiments,
remediation logs, or superseded proposals. The audit trail must remain intact,
but it should live in clearly labelled history and evidence material rather
than in the active method.

This is a documentation-only follow-on to the frozen v2.0 release. It must not
change a constituent, weight, input, formula, threshold, or source verdict.

## End state

The repository will have four unambiguous layers:

1. `index-methodology.md`: the binding, current v2.0 rules only.
2. `data/README.md`: the current input schema, validation rules, and sourcing
   protocol only.
3. `source-knowledge-base.md`: the binding evidence-retention and source-
   authority rules.
4. `docs/`: concise current rationale plus a visibly separate historical
   archive containing research, rejected designs, amendment detail, and
   remediation records.

`README.md` will orient a new reader, identify the current release and frozen
snapshot, and link to those sources of truth. It will not duplicate the
methodology.

## Work plan

### 1. Inventory and classify every document

Create `docs/document-register.md` with one row per Markdown or JSON research
artifact and one of these dispositions:

- **binding** — defines current behavior;
- **current rationale** — explains an active v2.0 decision without redefining
  it;
- **evidence** — retained inputs or calculations supporting a current rule;
- **historical** — superseded proposal, experiment, incident, or amendment;
- **delete** — generated duplication or a dead end with no audit value.

Record the replacement or archive destination before moving anything. Search
inbound links and code references first so no deletion creates a dangling
reference.

### 2. Rewrite the binding methodology as a final v2.0 specification

Rewrite `index-methodology.md` around the live calculation sequence:

1. scope, eligibility, dates, and data cut-offs;
2. source and missing-data rules;
3. Gate 1 asset eligibility;
4. Gate 2 capital resilience;
5. base score and portfolio optimisation;
6. delivery-rating exclusions and caps;
7. diversification, liquidity, turnover, and rebalance rules;
8. publication, governance, and corrections.

Keep only active definitions, equations, thresholds, precedence rules, and
failure behavior. Each rule gets a single normative definition. Examples stay
only where they resolve a real ambiguity. Move long rationales, empirical
results, rejected alternatives, issue narratives, and superseded language to
history.

Replace the long amendment narrative with a compact version table linking to
`docs/history/methodology-amendments-v1-v2.md`. The historical file preserves
the full rationale and original effective dates.

### 3. Consolidate current rationale and archive the rest

Create these concise current documents only where the binding method needs
supporting explanation:

- `docs/v2.0-capital-resilience-rationale.md` — final Gate 2 design and its
  evidence, replacing the overlapping capital proposal, production decision,
  coverage audit, source register, and continuous-capital plan narratives;
- `docs/v2.0-guidance-delivery-rationale.md` — final scoring logic, treatment
  table, and evidentiary boundary, with the claim-level candidate JSON retained
  as evidence;
- `docs/v2.0-validation.md` — the release checks, replay result, and known
  limitations.

Move superseded and process-heavy material beneath `docs/history/`, grouped as
`methodology/`, `research/`, and `remediation/`. Archived documents receive a
banner stating that they are non-binding and naming the current replacement.
Do not rewrite their substance in a way that would falsify the decision record.

### 4. Remove duplication from entry-point documentation

Reduce `README.md` to the investment objective, current release, high-level
construction flow, reproducible build commands, repository map, and links to
the binding sources. Replace embedded historical results with a link to the
frozen v2.0 snapshot.

Reduce `data/README.md` to the accepted schema and current field-specific
sourcing rules. Move design history and resolved migration notes to the archive.
Keep `data/config.json` machine-focused; move long explanatory prose that is not
consumed by the engine into the relevant current rationale document. Every
remaining parameter must still pass the strict consumer audit.

### 5. Remove implementation dead ends conservatively

Use reference searches, coverage, the configuration audit, and snapshot replay
to identify tools, config aliases, compatibility branches, and reports that no
current workflow consumes. For each candidate:

1. document its last consumer and replacement;
2. deprecate it in one cleanup commit;
3. remove it only after the full test suite and v2.0 replay pass without it.

Generated duplicates may be deleted. Source artifacts, claim ledgers,
point-in-time snapshots, and provenance records may not be deleted or rewritten
as cleanup.

## Initial disposition map

| Current material | Disposition |
|---|---|
| `index-methodology.md` | Rewrite as concise binding v2.0 specification |
| `README.md` | Rewrite as short current entry point |
| `data/README.md` | Trim to current schema and sourcing protocol |
| `source-knowledge-base.md` | Keep binding; remove duplication elsewhere |
| Capital-resilience proposal, audit, register, and decision documents | Consolidate current rationale; archive originals |
| Guidance research brief and dated study | Consolidate current rationale; retain claim-level JSON as evidence; archive narratives |
| Issue replay, remediation plan, sourcing brief, and claim-resolution pass | Archive as non-binding process history |
| Grade-tonnage survey and producer-impact analysis | Retain as evidence or archive according to active inbound references |
| `knowledge/` ledgers and artifacts | Preserve unchanged |
| `snapshots/` | Preserve as immutable release evidence |

## Acceptance criteria

- One active definition exists for every v2.0 rule, and it is in the binding
  methodology.
- The active methodology contains no rejected design, open issue that is already
  resolved, or chronological development narrative.
- Every archived document is visibly non-binding and links to its replacement.
- The README does not state weights or statistics outside a named frozen
  snapshot.
- No current file links to a moved or deleted path.
- `git diff` against the v2.0 snapshot shows no weight or input change.
- Compilation, all unit tests, gaps, provenance, strict configuration audit,
  and strict knowledge-store audit pass.
- A replay using the frozen v2.0 inputs reproduces the release weights to the
  engine's recorded precision.

## Delivery sequence

Ship this as a documentation-only v2.0.1 cleanup after v2.0 is frozen. Use small
commits in this order: inventory, archive moves, binding-method rewrite,
entry-point rewrite, current-rationale consolidation, then demonstrably dead
code removal. Validate after each behavior-adjacent commit so a prose cleanup
cannot silently become a methodology amendment.
